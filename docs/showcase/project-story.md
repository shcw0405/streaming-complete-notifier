# 项目来源、开发历程与未来规划

## 回答完就通知：一个从“等 AI”开始的小工具

“回答完就通知”的起点，是一个非常具体的日常困扰。

我经常把需要几分钟甚至十几分钟的任务交给 AI。一直守着页面，注意力被无意义地占用；切到其他窗口，又很容易开始处理另一件事，甚至顺手刷起手机。等我想起原来的任务时，答案可能早已生成，或者 Agent 已经因为缺少信息停在那里很久。

于是我产生了一个很朴素的想法：AI 回答完之后，能不能像收到一条消息一样提醒我？

最初，我以为这只是一个很小的浏览器插件：监听请求，结束时弹出通知，再播放一段提示音。但真正使用后，我发现“回答完了”并不是一个统一、稳定的状态。

不同 AI 平台使用不同的请求路径和流式协议；某些极短的预检请求会让通知刚提问就响；长思考模型会经历思考结束、开始回答和全部完成等多个阶段；图片生成也有成功、中断和下载等不同信号。更棘手的是，浏览器会限制后台标签页，用户一旦切走，页面本身就可能暂停工作。

这些问题推动项目不断演进。它从最初的完成通知，逐渐加入 ChatGPT 流式事件解析、思考结束提醒、Gemini、Grok 和 AI Studio 支持、通知标题中的原始提问、后台保活、图片生成状态检测，以及面向 Claude Code 和 Codex 的终端提醒方案。

项目没有构建复杂的使用流程。用户依然只需要像往常一样向 AI 提问，然后去做别的事情。真正完成时，一声提示音和一条桌面通知会把人拉回原来的任务；点击通知，还能直接返回对应标签页。这种“不改变习惯”的轻量体验，是我一直希望保留的部分。

开发过程中最大的感触，是一个看起来很简单的需求，往往隐藏着大量真实世界的边界条件。很多时间并没有花在增加新的按钮，而是花在减少一次误报、补上一类漏报，或者让后台页面更加可靠。也正是在这些反复验证中，我开始意识到，项目解决的并不只是通知问题。

当 AI 只能回答几秒钟时，人可以守着它；当 Agent 能够独立思考十五分钟、执行一小时甚至在后台持续运行时，人和 AI 之间就需要一种新的协作节奏。人应该可以放心离开，同时在结果产生、任务失败或需要决策时及时回来。

评委老师的反馈进一步明确了这个方向。老师指出，单纯的完成通知已经比较常见，项目更有价值的问题是：在多工具、多 Agent 的工作环境中，人怎样知道何时应该介入？不同 Agent 产生的上下文和材料怎样共享？提醒又能否从一条消息，变成人参与决策的入口？

因此，项目下一阶段不会只增加更多网站，而会把“完成”扩展成一组关键状态：已完成、需要输入、等待决策、执行异常。未来，用户可以直接从通知中批准、拒绝、补充信息或接管任务。

更长期的愿景，是成为人与多个 Agent 之间的统一介入层。一个人可能同时让不同 Agent 编写代码、检索资料、完成设计和整理文档。人不需要逐个窗口查看进度，而是在一个入口中理解状态、处理请求，并把工作继续向前推进。

这个项目从一句非常简单的话开始：“回答完就通知我。”

但我现在更希望它最终能够做到的是：**Agent 需要你时，就通知。**

## 适合放在海报或报名表中的精简版

“回答完就通知”源于一个真实痛点：等待 AI 会浪费注意力，切走后又容易忘记回来。项目通过识别 ChatGPT、Gemini、Grok 和 AI Studio 的真实生成状态，在任务完成时发送桌面通知和提示音，并支持长思考、图片生成、后台标签页和终端 AI 助手等场景。

开发中我逐渐发现，“什么时候算完成”并没有统一答案。不同平台、流式协议、后台休眠以及预检请求带来了大量漏报和误报问题。项目也因此从一个简单提醒器，演进成对 AI 任务状态的持续识别。

评委老师建议进一步关注人如何介入 Agent 工作流。未来，项目将从“完成通知”扩展到“需要输入、等待决策、执行异常”等关键节点，并探索成为人与多个 Agent 之间的统一介入入口。
